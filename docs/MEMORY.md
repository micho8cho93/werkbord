# Local memory (Phases 1A and 1B)

Memory is a private, local foundation in the controller's existing `werkbord.db`.
It adds no network service, HTTP/MCP route, controller-token grant, agent tool,
Team dependency, prompt injection, automatic extraction or LLM call. Nothing
collects records automatically. Existing runs, handoffs, projects and workflows
continue to work as before. Memory mutations do not append to the existing
event/SSE stream, so those consumers do not gain access to private memory.
Phase 1B adds a controller-owned observer that invalidates existing records
using committed Git state, existing durable events and authenticated GitHub metadata.

The implementation follows the existing dependency direction:

- `internal/domain/memory.go`: records, evidence classes, validation, limits,
  normalized structured details and deterministic evidence fingerprints.
- `internal/service/memory.go`: an owner-bound local service, repository and
  source validation, scope isolation, reference checks, quotas and retention.
- `internal/store/store.go`: `MemoryRepo` on the existing transactional `Tx`.
- `internal/store/sqlite/memory.go`: SQLite repository implementation.
- `internal/store/sqlite/migrations/0017_memory.sql`: additive migration,
  constraints, indexes, usage accounting and FTS5 triggers.

This is Individual code. It is reusable by local controller use cases through
Go interfaces, not a new shared package or permission for Team to import
Individual code. A future Team memory design must respect `STRUCTURE.md`.

## Records and authority

| Field | Meaning |
| --- | --- |
| `id` | Random stable `mem_…` identifier, generated by the service |
| `scope.ownerId` | Stable individual local principal supplied by the trusted caller |
| `scope.projectId` | Optional registered project ID, never its display name |
| `scope.repository` | Optional canonical Git remote identity, never a checkout/common-directory path |
| `type` | Caller-defined identifier, e.g. `build_command` or `workflow_convention` (1–128 ASCII identifier characters) |
| `authority` | Exactly one of the evidence classes below |
| `source` | Structured provenance, including source type and required reference |
| `summary` | Required trimmed UTF-8 text, at most 4,096 bytes |
| `details` | Optional JSON object; normalized to `{}` when absent, at most 16,384 bytes before and after normalization |
| `state` | `current`, `needs_verification`, `historical` or `superseded` |
| `sensitivity` | `private`, `sensitive` or `secret` |
| `sharingEligible` | Metadata for possible later review; **never permission to share** |
| `verifiedAt` | Optional explicit verification instant; never automatically stamped by persistence |
| `supersededBy` / `duplicateOf` | Optional scoped references to other memory IDs |
| `fingerprint` | SHA-256 of normalized evidence, including provenance and privacy metadata |
| `schemaVersion` | Record shape version, currently 1; separate from migration version |
| `version` | Compare-and-swap revision, initially 1 |
| `createdAt` / `updatedAt` | Controller timestamps, immutable creation time and monotonic update time |

Authority is a closed vocabulary, separate from caller-defined memory type:

| Authority | Interpretation |
| --- | --- |
| `factual_observation` | Recorded evidence of an observation; not proof that it is still true |
| `inferred_preference` | An inference; never a user decision or instruction |
| `explicit_decision` | A user decision with explicit user provenance and approval references |
| `approved_policy` | A policy with explicit user provenance and approval references |

Decisions and policies require source type `user`, `approvedBy` and
`approvalRef`. These fields record the trusted caller's evidence; this layer
does not implement an approval UI, authenticate those assertions or enforce
policies. Type, authority and source type cannot change through Update. A new
authority requires a separate record with its own provenance. Changing decision/policy
summary or details also requires a new approval reference. Links must
preserve both type and authority, so an inference cannot supersede a policy.

All timestamps are stored as UTC Unix milliseconds.

Defaults are `needs_verification`, `private`, and sharing ineligible. Sensitive
and secret records cannot be marked sharing eligible. All records remain local
and private, including explicitly eligible records. Changing evidence while
carrying forward the same verification timestamp clears that timestamp; a
caller can explicitly supply a new verification time. Verification cannot be
in the future relative to the update timestamp. It is independent of authority.

Provenance supports:

- `type`: `user`, `git`, `run`, `handoff`, `import`.
- `reference`: required bounded source reference, up to 2,000 bytes.
- `gitSha`: full lowercase SHA-1 or SHA-256 commit ID, required for Git sources.
- `branch`: optional unambiguous full `refs/heads/...` or `refs/remotes/...` ref.
- `paths`: up to 64 unique repository-relative files or directories, each up to
  2,000 bytes. Paths are sorted during normalization and included in fingerprints.
  Absolute paths, traversal and globs are not interpreted as source selectors.
- `pullRequest`: optional credential-free HTTPS PR reference, up to 2,000 bytes.
- `runId`: optional local run ID; checked against the project when supplied.
- `handoffId`: required for a handoff source. Existing handoffs have no separate
  ID, so this is the run ID, and that run must currently have a handoff.
- `approvedBy`: bounded principal identifier, and `approvalRef`: bounded explicit
  approval reference for decisions and policies.

Git and PR evidence requires repository scope. Local run/handoff evidence
requires project scope. The CRUD service makes no Git/GitHub/network call and does
not claim that a SHA exists, that a PR is genuine, or that imported observations
are controller-verified. A handoff reference identifies the run's artifact;
its content can subsequently be edited. Include any required snapshot in bounded
`details`. Provenance links are not foreign keys into runs: later run retention
does not erase the memory or its source reference.

## Scope and repository identity

Every get, list, search, update, delete, link and deduplication query uses an
**exact** `(ownerId, projectId, repository)` partition. An empty component is
not a wildcard. Personal, project-only, repository-only and combined project /
repository scopes are independent. List does not automatically inherit personal
or project memories into another partition. The service is bound to one owner;
a different explicit owner returns `ErrForbidden`, and another scope's ID is
`ErrNotFound`.

Repository addresses reuse `integration.RepositoryIdentity`. For example,
`git@GitHub.com:acme/tool.git` and `https://github.com/acme/tool` both become
`github.com/acme/tool`. Path case and non-default ports remain significant.
Returned canonical identities can be supplied directly on subsequent calls;
they are revalidated through the same validator. Credentials, local paths,
traversal and display names are refused. No filesystem identity or display name
is used as a fallback. Local repositories without a usable remote can still
have project-only memories.

Creating combined project/repository memory checks the canonical identity
against the project's saved remote snapshot. Work projects cannot acquire
repository scope. Reads, updates and deletes remain available in the original
partition after remotes change; records are not silently moved to another
repository. Local run references are checked against the named project.

## Go service API

Construct the service with the existing `service.Deps` and a stable local owner
identifier (not a person's changeable display name). There is no new process or
database handle. The application has no individual account registry yet; the
trusted caller must persist/reuse its chosen local principal.

```go
memory, err := service.NewMemory(deps, "local_person", domain.MemoryLimits{})
// Zero limits selects DefaultMemoryLimits; otherwise supply all three fields.
scope := domain.MemoryScope{
    ProjectID: projectID,
    Repository: "git@github.com:acme/tool.git",
}
record, err := memory.Create(ctx, scope, domain.MemoryContent{
    Type: "build_command",
    Authority: domain.MemoryObservation,
    Source: domain.MemoryProvenance{
        Type: domain.MemorySourceUser,
        Reference: "local-note:build-command",
    },
    Summary: "Run make check before release",
})
```

| Method | Contract |
| --- | --- |
| `Create(ctx, scope, content)` | Normalize, validate and insert; return record or `ErrDuplicate` for exact canonical evidence |
| `Get(ctx, scope, id)` | Read one record in the exact scope |
| `FindDuplicate(ctx, scope, content)` | Return canonical record for normalized evidence; no mutation |
| `List(ctx, scope, query)` | Scoped list/search, optional type/authority/state filters, paginated |
| `Update(ctx, scope, id, version, content)` | Replace content, require current version, increment version atomically |
| `Delete(ctx, scope, id, version)` | Explicit physical row deletion with version check; referenced records return `ErrConflict` |
| `Usage(ctx)` | Current owner's stored record count and logical record bytes across all scopes |
| `Prune(ctx, limit)` | Explicit retention sweep of 1–1,000 eligible records for the bound owner |

Sentinel errors use `domain.ErrInvalid`, `ErrNotFound`, `ErrForbidden`,
`ErrDuplicate` and `ErrConflict`; use `errors.Is`. Quota failures are conflicts
and roll back all writes, including the FTS index and usage counters. A
successful record update increments its version exactly once. Stale updates
and stale deletion cannot overwrite or erase newer data.

`List` accepts `MemoryQuery{Text, Type, Authority, State, Limit, After}`. The
default page is 50 records, with a maximum of 100. Order is creation time
descending, then ID descending; `Next` is an optional `(createdAt, id)` keyset
cursor. Page traversal avoids offset drift. Concurrent inserts before the
cursor require a fresh traversal; pages are separate read snapshots.

## Deduplication and links

Details are canonicalized with sorted object keys, without rounding JSON
integers. Fingerprints include type, authority, source/provenance, summary,
details, sensitivity and sharing eligibility. They exclude lifecycle,
verification timestamps and links. Exact evidence therefore cannot be
reinserted as another canonical record simply by changing its state; update
that record explicitly. Different provenance, authority or privacy metadata
stays separate. This is exact evidence deduplication, not semantic similarity.

The partial unique index enforces one canonical record per fingerprint per
scope. An explicitly linked `duplicateOf` record may retain separate text and
provenance as a caller-reviewed duplicate. `FindDuplicate` returns canonical
records only. No creation silently edits another record or changes its privacy.

A superseded record must name its replacement; other states cannot carry a
supersession link. A record cannot carry both link kinds. Composite foreign
keys enforce exact owner/project/repository isolation and restrict deletion
of referenced targets. The service rejects cycles and reference paths beyond
100 hops. Unlink references explicitly before deleting a target. Supersession
is a caller-directed update of the older record; it does not modify the target.

## SQLite, search, bounds and retention

Migration 0017 only creates new tables, indexes and triggers. The existing
migration loader, pre-upgrade backup, transactional writer and WAL read pool
are reused. Existing application tables are unchanged. `schemaVersion` is
record metadata; SQLite migration version remains managed by `schema_migrations`.

The pinned pure-Go `modernc.org/sqlite` build supports FTS5, exercised by the
integration tests. The content table has an explicit integer primary key for
stable FTS row IDs across VACUUM-based backups, separate from its unique public
`mem_…` ID. `memories_fts` is an external-content FTS5 index over summaries
only, with `unicode61` tokenization and diacritic removal. Transactional triggers
keep creation, summary edits and deletion in sync. Search treats each
whitespace-delimited term as a quoted literal phrase, joins terms with AND and
binds the expression as an SQL parameter. Caller FTS syntax, operators and
prefix wildcards are not executed. Search is limited to 256 UTF-8 bytes and
16 terms, and results always pass the exact scope filter. Details and provenance
are not full-text indexed. Results use creation order, not relevance ranking.

Indexes cover exact scope with pagination order, state/type/authority filters,
scoped fingerprints, owner/state/age retention, and both incoming link types.
`memory_usage` is a singleton global counter maintained in the same transaction
by triggers. Owner usage is aggregated through the owner-prefixed indexes.

Explicit content writes cap a serialized complete record at 32 KiB, in addition to individual
field limits. Default per-owner limits across all scopes are 10,000 records
and 32 MiB of logical record bytes. Constructor configuration can set:

- Record count: 1–100,000.
- Logical bytes: 32 KiB–256 MiB.
- Historical retention: 1 day–10 years; default 180 days.

SQLite triggers additionally enforce global hard ceilings of 100,000 records
and 256 MiB of logical bytes across owners. Capacity never silently evicts
current records. Explicit deletion and pruning free logical capacity.

`Prune` only removes historical/superseded records whose update time is strictly
older than the configured cutoff and which have no incoming memory links.
Current and needs-verification records are retained regardless of age. Recent
history, referenced targets and other owners are preserved. A later sweep may
remove a target after its old referencing records have been pruned. Maintenance
is explicit, not scheduled or run automatically on reads/startup/writes.
Changing retention therefore does not immediately delete records.

Background invalidation retains the existing logical payload charge so a full
quota cannot prevent a fact becoming stale. It only changes the fixed lifecycle
state, update time and CAS version; the bounded extra metadata bytes are storage
overhead until the next explicit content write recalculates the charge.

Limits bound logical payload growth, not the entire SQLite file. FTS/index/page
and WAL overhead, free pages, existing application data and backups are additional.
There is no automatic VACUUM or secure erasure. Deleted text can remain in old
pages/WAL/backups until their existing lifecycle removes it. OS-level private
data-directory permissions protect the database; sensitivity is classification,
not per-record encryption.

## Backup, restoration and validation

Memory tables, counters, links and FTS data travel with the same SQLite database
and its consistent backups. Do not copy a live main database without accounting
for WAL; use the existing consistent backup mechanism. Restore offline through
the existing database workflow. Restoring a pre-0017 backup then opening it with
this build applies 0017 and retains earlier application data, with empty memory.
Restoring a current consistent snapshot retains memory and its search index.
An older build still refuses a database with an unknown newer migration.

Tests cover validation and conservative defaults, authority separation,
repository canonicalization, exact scope isolation, duplicate fingerprints,
explicit links/cycles, FTS literal queries and lifecycle, keyset pagination,
conflicting concurrent writes, versioned deletion, field/record/quota bounds,
retention and owner isolation, transaction rollback, migration with existing
data, restart, pre-upgrade restoration and current snapshot restoration with
FTS integrity checks. Run:

```sh
go test ./internal/domain ./internal/store/sqlite ./internal/service ./internal/archtest
go test -race ./internal/domain ./internal/store/sqlite ./internal/service -run Memory
```

## Remaining scope

There is no UI, CLI or remote API, automatic harvesting from runs/handoffs,
retrieval into agent prompts, semantic search,
embeddings, external database, sharing/Team sync or policy enforcement. Local
callers configure limits in Go; there is no new settings screen or environment
variable. Approval and verification assertions must come from a trusted local
caller; these are not authentication credentials. Future consumers must perform
their own explicit context selection, approval and privacy checks before using
or sharing memory.


## Phase 1B: Git observation and reconciliation

The controller owns `service.MemoryFreshness` alongside `GitHealth`. It shares
Git Control Center's registered-repository resolution, the same `gitrepo.Control`
instance, read-only Git plumbing and authenticated GitHub client. There is no
second Git implementation, hook installation or public webhook receiver. It
never calls fetch, pull, push, merge, branch creation, checkout or worktree
mutation. Existing user-requested operations continue to own those actions.
Uncommitted/index/untracked files are not inspected by the observer and never
become verified durable state.

The pipeline is:

1. Existing operations commit their audit/lifecycle events with their records,
   then publish through the existing non-blocking broker. Relevant Git actions,
   inspections, worktree changes and run transitions wake the memory worker.
2. Authenticated PR reads share `GitControl.readPullRequests`. A changed bounded
   PR collection writes `git.pull_requests_observed` and a deduplication digest
   atomically. This includes creation, updates, merge/closure state and GitHub's
   independently observed CI/check rollup, with PR head SHA. Identical reads do
   not duplicate events. These events carry GitHub metadata, never memories.
3. One serial background worker traverses only existing project/repository
   memory partitions. Event hints prioritize the affected project and matching
   repository-only partitions, alternating with the normal scan so a busy
   project cannot starve other repositories. Only one pending project hint is
   retained; durable replay/polling covers bursts. It subscribes before starting,
   scans on startup and wakes
   every 30 seconds by default. Timer reconciliation discovers external commits,
   branch creation/deletion/checkout, local HEAD movement, rebases and changed
   remote-tracking refs without contacting a Git remote. Fetch/push observations
   cover only refs that existing integrations have actually updated; the observer
   makes no claim about an unfetched server state.
4. It reads committed HEAD, the checkout branch and local/remote-tracking refs,
   checks HEAD, repository identity and refs again for an observation race, then reads bounded authenticated
   PR metadata when available. It replays durable project events after the saved
   cursor, independently of broker delivery. Missing transcript/audit retention
   (`ReplayFloor`) is treated as an evidence gap, never as proof nothing changed.
5. Facts are checked against their source commit and named branch (or current
   checkout HEAD when no branch is supplied). An ancestor check precedes the
   bounded committed-tree diff. Changed files and both sides of renames are
   matched against exact source paths and directory prefixes. With no paths,
   any committed file change is relevant. The previous successful revision is
   compared too, so resetting a branch onto an old source commit does not hide
   a history rewrite. A deleted source branch is unknown even if the source
   object still exists. Recorded branch-deletion and PR-change events also catch
   observed changes that a later snapshot could otherwise mask.
6. In one database transaction, affected `current` records become
   `needs_verification` and their CAS version increments. The private checkpoint
   and invalidations commit together or roll back together. Replays only touch
   still-current records, so they cannot duplicate records or repeatedly update
   already stale facts. Git/network I/O happens outside write transactions.

### Lifecycle and evidence

A source change means a fact **needs verification**, never that it is false.
The observer never promotes a record to `current`, sets `verifiedAt`, changes
its claim, rewrites its original provenance, supersedes it or deletes it.
`verifiedAt` remains the last explicit verification instant; consumers must
respect `state` rather than treating that timestamp as current proof. Recovery
from an outage does not automatically restore stale facts. A trusted caller can
explicitly review/update them through the existing versioned memory service.

Historical and superseded records remain historical. Explicit decisions and
approved policies retain their authority and lifecycle even when implementation
files change: the fact that a decision was made is historical evidence. The
observer never erases architectural decisions or infers a new approval.

Missing source commits, non-ancestor histories (force-push/rebase/reset), missing
branches, truncated diffs, comparison-budget exhaustion and inaccessible or
ambiguous repositories conservatively invalidate potentially dependent facts.
Observations scoped to a repository or a Git project without a commit anchor
also need verification, unless a person wrote and confirmed the statement
themselves (source `user`): it names nothing in Git to compare, so it is left as
confirmed until they correct or delete it. Paths or a branch name alone cannot
establish committed source evidence.
Unrelated path-linked facts remain current when complete Git evidence proves
no overlap. Personal notes and unanchored preferences are independent
of repository code. Work projects have no repository and are excluded.
Code-linked preferences follow their source evidence.

Run completion/failure/stop events invalidate linked run facts when newer than
the recorded claim (creation or last explicit verification, not an unrelated
content/privacy edit). A successful run exit and handoff/agent text are **not**
independent evidence that tests passed. Phase 1B observes independently reported
CI through authenticated GitHub PR check metadata; it introduces no local test
executor and mines no claimed test results from agent transcripts. Passing CI
still never automatically verifies a natural-language claim. A missing/offline
GitHub connection or PR omitted from the bounded list makes PR-linked facts
uncertain, not closed, merged or fresh. Local facts can still be reconciled.

Exact owner/project/repository isolation remains unchanged. Combined scopes
must match the registered checkout's current canonical remote identity.
Repository-only scopes resolve uniquely against at most 64 saved repository
snapshots. No match, multiple matching projects, more than 64 possible snapshots,
a replaced checkout or a changed remote identity is ambiguous: no arbitrary
checkout is chosen. These cases keep their successful revision/cursor and mark
potentially dependent facts for verification.

### Durability, bounds and recovery

Migration `0018_memory_freshness.sql` adds private `memory_freshness` checkpoints
in the same database and backups. Each exact partition stores:

- Last completely processed committed revision (HEAD, branch and ref map), PR
  signatures/availability, durable event cursor and successful observation time.
- Pending observation, event cursor, keyset record cursor and an uncertainty
  flag so large traversals resume across restarts.
- Last attempt time, bounded diagnostic code and checkpoint CAS version.

A successful revision/event cursor advances only after a full traversal. Failed
repository observations retain the previous successful values. If evidence
moves mid-traversal, remaining pages are conservatively invalidated and another
pass starts; cursors are not continually reset in a busy repository, so the tail
cannot starve. Newly inserted records are picked up on the following pass.
Continuous reconciliation also checks newly added/current records even if HEAD
has not moved since the last checkpoint. Checkpoints disappear when the last
record in their partition is explicitly deleted or pruned.

Each worker batch covers at most 8 partitions, each reconciliation at most 100
current records and 256 durable events. Further pages/batches continue after
100 ms. Git comparisons share a cache capped at 16 commit pairs per page;
diffs are capped at 1,000 paths and existing Git output/process ceilings apply.
Ref snapshots are capped at 2,048 refs and 256 KiB before PR signatures; each
checkpoint is at most 1 MiB. Git observation has a 10-second deadline and GitHub
reads a nested 3-second deadline and at most 40 PRs / 256 KiB of metadata. Unknown evidence after any ceiling causes
conservative invalidation instead of an empty successful diff. SQL scope and
record traversal use bounded keyset queries, not an unbounded in-memory queue.

Broker delivery is only a wake-up hint. Dropped subscriptions resubscribe and
schedule another pass; startup, durable replay and polling recover missed events
and offline periods. Compare-and-swap conflicts roll back the whole page for a
later retry. The worker runs independently of run/Git request completion and
is cancelled/joined before the broker and database close. No public memory API,
agent context injection, automatic fact harvesting or Team dependency is added.

Real-Git and SQLite tests cover relevant/unrelated paths, directories/renames,
uncommitted files, branch creation/checkout/deletion/reset, remote-tracking
movement, replay idempotence, database restart without events, retained-event
gaps, completed runs, authenticated PR/CI changes, missing evidence, remote
identity changes, unavailable/large/truncated repositories, resumable pages,
continuously moving repositories, read-only observation, atomic checkpoint CAS,
upgrade from Phase 1A, polling and shutdown. Run:

```sh
go test ./internal/domain ./internal/store/sqlite ./internal/service ./internal/controller
go test -race ./internal/domain ./internal/store/sqlite ./internal/service ./internal/controller -run 'Memory|RepositoryHealth'
make check
```

## Phase 1C: deterministic knowledge and context retrieval

Individual's controller now owns `service.Knowledge`, bound to the stable local
principal `individual`. This is the owner of this controller's private data, not
a Team identity or a principal supplied by an HTTP request. The worker and UI
reuse the existing memory service, structured run handoffs, saved task history,
Git Control reader and freshness observer. Team has no dependency on them.

### Extraction and verification

A serial worker scans terminal runs, including existing history. Each run batch
loads at most four candidates. In one write transaction it re-reads the run,
extracts the claims, records evidence and saves the extracted run version. A
crash, cancellation, CAS error or quota failure rolls back the entire batch for
that run. A persisted keyset cursor advances past failing candidates, wraps and
retries them, so an invalid handoff or a full partition cannot starve later runs.

The extractor saves a concise controller-observed lifecycle fact: task ID/title,
run ID, terminal state and process exit code when available. **Completed and exit
code zero say nothing about whether tests passed.** Agent-reported HEAD values,
free-text handoff Git state and changed-file lists are not independent proof.

Only structured decisions, tests, known issues, blockers, unanswered questions,
next action and structured results are extracted from handoffs. The generated
lifecycle prefix is removed from results; manually edited results are still
unverified handoff evidence.
These become `factual_observation` candidates in `needs_verification`, presented
as **suggestions / unverified**. A claim that looks like a credential, token,
connection string with a password or a local path (`integration.LooksSensitive`,
the screen Team's wire validation uses too) is stored with sensitivity `secret`,
so no retrieval, source listing for the assistant or publication path serves it.
Saving such text by hand is refused. A reported decision is never an
`explicit_decision`; a reported test never gains verification through repetition,
completion, pinning or a successful CI check. Results are potential solutions,
not a controller judgment that a solution worked. The extractor skips the
fallback transcript summary, source diffs, empty values, default next-action
boilerplate, overlong fields and fields beyond the first eight items of each
structured category. Each extracted claim is at most 1,024 UTF-8 bytes.

Four saved repository snapshots per batch bootstrap Git observations even before
a project has memory. Canonical origin identity (or one unambiguous remote) is
resolved and checked live through the existing freshness observer. Only a
complete observation produces a verified fact of the form “Observed repository
HEAD … on …”. Earlier HEAD observations become historical. Returning to a previously observed
HEAD can reverify the identical controller fact; user edits, archives and deletion
tombstones are never undone by this verification. Refs/PR reads retain
the freshness observer's existing output and deadline limits. No Git fetch,
mutation, transcript parsing, local test execution or network/model dependency
is introduced. CI evidence remains available through Phase 1B's existing durable
Git observations; it is never used to verify an unrelated natural-language claim.
Lifecycle facts depend on run transitions, rather than changes to repository
files. All other code freshness rules from Phase 1B continue to apply.

### Evidence, duplicates and compaction

Migration `0019_memory_knowledge.sql` adds private evidence records, run-version
checkpoints and pin metadata. Each evidence item stores a stable hashed source
identity, original structured provenance, a bounded excerpt and observation time.
Handoff references identify the run, field and version at first extraction.
Source identity uses run ID, field and normalised claim, excluding version and
array position: a refresh or reorder cannot manufacture another observation.

Compaction happens during extraction, inside the same transaction. Identical
normalised text in the same exact owner/project/repository, type, authority and
source category shares a recommendation. Normalisation collapses whitespace;
it preserves case, negation, numbers, commands and paths. This intentionally
under-merges paraphrases instead of guessing that distinct claims mean the same
thing. It uses no embeddings or probabilistic similarity threshold.

A recommendation links at most 64 evidence observations. Further observations
start another bounded record. Original sources and verification never change
when another agent agrees. Evidence applicability is tracked separately from
immutable source content. Editing a handoff deactivates its old observations;
candidates with no applicable observations become historical in pages of at most
100. Manual archiving and corrections are never undone by extraction. Historical
records stay inspectable separately from the recommended current knowledge.

Deleting a memory removes its excerpts and provenance from the evidence table,
leaving only content-free source hashes and small bookkeeping fields. The
controller's database is opened with `secure_delete`, and deleting or pruning
memory merges the full-text index, so a deleted summary is no longer readable in the
database file once the write-ahead log is checkpointed (tested by reading the
file). Earlier consistent backups and the original run handoffs are separate copies. Those
identities suppress recreation from replayed history. Original runs/Git objects
are unaffected. A genuinely new run remains a new observation. Tombstones count
against evidence limits rather than accumulating without bounds.

### Manual knowledge and settings

Project Settings → **Memory** provides a list and literal word search with status
filters, source inspection, pin/unpin, correction, archive and versioned deletion.
Work projects can save manual memory too. Search returns at most 100 records and
asks the user to narrow a full result set. This is a small settings section, not
a separate dashboard. It follows the existing desktop-only settings convention.

“Save a memory” and “Correct” explicitly confirm a decision, preference, fact or
policy. The server assigns owner, approval identity/reference, source and
verification time; the HTTP body cannot assert those fields. A correction creates
a new user-sourced record and atomically archives the previous one. Both its
confirmation and a snapshot of the original provenance/excerpt are linked to the
new record. Corrections preserve the original sensitivity and never implicitly
declassify sensitive/secret records. Removing the archived recommendation does not erase the reason
for the correction. Pinning affects ordering and retention, never authority.

The local owner-authenticated endpoints are:

- `GET/POST /api/projects/{pid}/memory`
- `PATCH/DELETE /api/projects/{pid}/memory/{id}` (requires `version`)
- `GET /api/projects/{pid}/memory/{id}/sources`
- `GET /api/projects/{pid}/memory/context`

List/context filters are `q`, `type`, `status`, `authority`, `repository`, and
`limit`. Sources/mutations take `repository` to identify an exact partition;
manual corrections include it in the request body. The API never accepts an
owner ID. Memory is disabled on the private-network listener; phone, MCP and
local-program grants acquire no memory permissions. The existing route-allowlist
tests enforce that those credentials cannot reach newly added endpoints.

### Retrieval contract and instruction boundaries

`Knowledge.Retrieve` accepts an owner-bound exact project, optional canonical
repository, memory type, authority, status, literal search, result limit and token
budget. SQL applies filters and ranks the complete matching set before loading
at most 100 candidates: pinned, verified, human-saved, FTS relevance and recency.
Explicit human knowledge therefore survives a stream of recent run observations. It avoids
letting a large set of recent observations hide an older pinned decision.

Default retrieval includes only current, non-duplicate, private records. Explicit
`includeUnverified=true` can add candidates; it never includes archived,
superseded or sensitive/secret records. Project existence and repository
ownership are rechecked. Live resolution fails closed for missing/replaced/
inaccessible repositories, and run/handoff sources must still exist in the
selected project. HEAD facts must still match the live checkout. A retrieval
checks at most four repository identities, each with a three-second deadline;
additional repositories are omitted conservatively. Historical/source browsing
uses the separate list and source endpoints.

Results carry a concise summary, source provenance, memory kind, pin state,
verification (`verified`, `human_confirmed`, `unverified`) and conservative
confidence (`high` for independent/human verification, `low` otherwise).
Preferences, suggestions, decisions, saved policies and verified facts are
explicitly distinguished. There is no numerical score pretending to measure
whether an agent's claim is true.

The budget defaults to 2,048 tokens, accepts 512–16,000, and counts serialised JSON
UTF-8 bytes as a deliberately conservative token upper bound, including the
boundary notice and provenance. Whole records are omitted when they do not fit;
text/provenance are not truncated into a misleading claim. `truncated` indicates
candidate/budget limits. No model or tokenizer is required.

Every response labels memory as untrusted contextual data that cannot override
system/user instructions or application permissions. Retrieval does not execute
text, modify agent system instructions, make policies authoritative, alter appops
permissions or inject memory into runs automatically. Consumers must preserve
this data boundary. The current provider architecture serves interactive agent
sessions, not an independently authorised memory summariser; Phase 1C adds no
model-assisted path or provider invocation. A future optional summariser must be
separately authorised and isolated from the deterministic path.

### Retention, limits and interruption recovery

The worker starts with the controller, polls every five seconds and has one
15-second maintenance deadline. An idle tick commits nothing, and a repository is
observed by it at most once every 30 seconds (using Git only, never a GitHub
request); pull-request metadata is read by the 30-second freshness worker. It reads at most four runs and four repositories
per tick, maintains durable scan cursors, retires up to 100 obsolete observations per run
and prunes at most 100 unpinned historical/superseded records older than the
configured retention (180 days by default). Pinned history survives pruning;
correction ancestors remain while their replacement records exist; current decisions/preferences are not evicted to make room for ingestion. Quota
failure preserves existing knowledge and retries later. Worker cancellation is
joined before the database closes.

The existing record limits remain. Owner capacity now includes evidence bytes;
evidence has separate ceilings of 50,000 identities per owner, 100,000 globally
and 64 MiB globally, with constant-time global byte accounting. Each source JSON
is at most 4,096 bytes, each excerpt 1,024 bytes. Evidence and extraction tables,
FTS, pins and checkpoints share the existing SQLite migration/backup lifecycle.
A delete keeps only a small quota-accounted replay tombstone. This is intentionally
conservative: exhausting those identities stops new extraction rather than
silently forgetting user deletions or dropping provenance.

Tests exercise structured extraction, independent Git versus agent evidence,
source/version replay, bounded compaction with all provenance, negation/case/
number distinctions, explicit corrections and retained original sources, archive/
delete replay, pin retention, quota rollback and restart/retry, literal search,
relevance/authority ordering, owner/project/repository isolation, inaccessible
sources, complete response budgets, protected API mutations, strict input fields
and unchanged credential allowlists. Validation:

```sh

go test -race ./internal/domain ./internal/store/sqlite ./internal/service ./internal/api ./internal/controller -run 'Memory|Knowledge|RepositoryHealth'
```

## Suggestion feedback (Phase 3B)

When a person marks a suggested next step *useful*, *not useful* or *dismisses* it, the controller keeps one bounded record per
project, intent and variant ([RECOMMENDATIONS.md](RECOMMENDATIONS.md#feedback)): type `recommendation_feedback`, authority
`inferred_preference`, state `needs_verification`, private, **not eligible for sharing**, with counters (at most 1,000) and at
most eight hidden suggestion ids that expire after 14 days. It is an inference about how suggestions should be ordered. It
is never a decision or a policy, cannot restrict or permit anything, is not part of the context given to the assistant, and
reaches Team only if the person writes and reviews a statement of their own for publication. It appears in the project's memory
list like any record; archiving or deleting it resets the preference.

## Phase 4A: repository relationships

A code repository still corresponds to a project. Relationships are lightweight,
versioned `repository_relationship` observation records in the existing private
memory store, scoped to their source project. There is no graph database or new
project registry. Each record's structured details contain:

- `source` and `target`: project ID plus canonical credential-free repository
  identity from the existing integration identity validator;
- `type`: `package_dependency`, `api_consumer` (consumer → provider),
  `shared_authentication`, `deployment_dependency`, or `manual_association`;
- `evidence`: `manual`, `package.json`, or `go.mod`, and optional full
  `sourceRevision` / `targetRevision` Git commit IDs;
- `inferred` and `lastVerified`. Memory supplies ownership, sensitivity,
  verification state, optimistic versions, deletion and optional supersession.

The owner can add, verify and remove links in Project settings → Relationships.
`GET /api/projects/{pid}/relationships?depth=2` traverses both incoming and
outgoing links, with a visited set and depth 1–4. It returns evidence, status and
an advisory compatibility recommendation. Both endpoints must still be registered
under their saved canonical identities before any result enters traversal. A
remote rename/replacement hides the old link until explicitly rebound; a display
name change preserves identity. Missing/deleted repository bindings do not appear.
A changed saved Git head or verification older than 24 hours makes a link stale;
unknown or inferred links stay provisional until explicitly accepted.

`POST /api/projects/{pid}/relationships` accepts `{relationship,accept}`.
`POST /api/projects/{pid}/relationships/{id}/accept` takes `{version}` and
rechecks both bindings. Removal uses the existing versioned memory DELETE.
`POST /api/projects/{pid}/relationships/discover` takes `{source,manifest,content,
revision}` from the owner's permitted manifest reader. Discovery parses bounded
manifest bytes deterministically; it performs no filesystem/network/Git operations.
It accepts only explicit credential-free Git URLs in npm dependencies,
devDependencies and optionalDependencies, or explicit Git URL replacements in
`go.mod`. Registry names, shorthand repository names, vanity module paths, relative
paths and package names are insufficient identity evidence. Only a uniquely
registered matching remote becomes a provisional package dependency; repeated
identical observations deduplicate. This deliberately misses dependencies that
cannot be established without guessing. No background scan of other machines or
registry lookup is introduced.

Salie's existing memory operation includes endpoint-checked relationships and
rechecks its own project grants before presenting them. Links suggest checking
compatibility or coordinating changes, never prove breakage and never authorise
Git actions. Relationships remain private unless a person separately reviews a
sanitised cross-repository Team memory proposal through the existing sharing API.
